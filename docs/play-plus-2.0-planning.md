# Play Plus 2.0 — 제품 기획 작업 문서

> **상태: DRAFT / 논의 중**
> 최초 정리: 2026-10-15
> 범위: 새로운 2.0의 방향, 특히 A(자막·재생 도구 완성도) 기능 후보 v0.1
> **이 문서는 canonical 제품 계약, 구현 승인, 범위·우선순위 확정 또는 릴리스 승인 문서가 아니다.**

## 1. 배경과 제품 방향

- 종전 미배포 Play Plus 2.0의 리브랜딩과 제품/구현 계획을 철회한다. 브랜드는 **Play Plus**를 유지한다.
- 새로운 2.0은 **배포된 v1.12.0의 사용자 행동과 최신 main의 개선 결과**를 출발점으로 다시 기획·설계한다. 과거 2.0 코드를 통째로 병합하거나 그 계약을 자동으로 계승하지 않는다.
- **A: 자막·시청·재생 도구의 완성도 향상**을 확실한 기반 방향으로 삼는다. 기존 사용자가 이미 하는 일을 더 쉽고 안정적으로 만들고 유용한 현재 기능·설정·단축키·자료를 보존한다.
- **B: 능동적인 언어 학습**(듣기, 연습, 복습 등)은 별도로 기획한다. A의 사용성을 희생해 B를 강제하지 않는다. 이전 게임형 Listening Mission의 구현 여부는 재도입 근거가 아니다.
- 사용자 피드백 기능을 2.0보다 먼저 공개할 계획이다. 그 피드백을 적극 참고해 2.0의 상세 범위·UX·우선순위를 확정한다. 기획 자체는 피드백 수집과 병행할 수 있다.
- **A 방향 채택은 아래 개별 후보를 모두 구현하기로 승인한 뜻이 아니다.** 이미 제공하는 기능은 중복 개발하지 않고, 실제 문제와 차이가 확인된 개선만 구체화한다.

### 2.2 후보 상태 표기

- **R (v1.12.0 기존)**: 이전 배포 기준의 사용자 기능. 유지가 기본이며 신규 기능으로 세지 않는다.
- **M (main 개선)**: v1.12.0 이후 B1–B6/N1–N6 등으로 현재 main에 이미 반영된 개선. 재구현하지 않는다. 배포 여부와는 별개다.
- **X (과거 2.0)**: 과거 미배포 2.0에서 구현·설계된 차이. 현재 main에 이식됐다는 뜻이 아니다.
- **P (개선 제안)**: 현재 대화에서 모은 신규 개선 가능성. 구현도 승인도 확정하지 않는다.
- **검증 필요**: 구현 경계, 실제 UX 또는 릴리스 태그 포함 여부를 추후 파일/테스트/Chrome으로 더 확인해야 하는 항목.

상태는 한 기능에 여러 개 붙을 수 있다(예: R+M). 특히 “이전 2.0에서 구현”과 “현재 1.12.0에 없음”은 동의어가 아니다. 구현 판단 전에 **최신 main에서 현행 동작을 다시 확인**한다.

## 4. 과거 2.0에서 발견한 재사용 자산과 주의점

## 5. 사용자 피드백 선행 배포 및 반영

### 5.1 별도 선행 작업

- [Issue #128](https://github.com/saramkim/play-plus/issues/128): Side Panel 내 자발적 피드백, 비강제 예고 배너, 메뉴 재접근, 명시적 제출, 작은 Cloudflare Worker/D1 수신, 90일 보관·삭제 정책.
- [PR #129](https://github.com/saramkim/play-plus/pull/129)의 코드가 2026-10-15 조회 시점 main에 병합되었다. **이 사실만으로 CWS 배포/실제 사용자 피드백 수집이 시작됐다고 간주하지 않는다.** 개인정보 안내, 실제 endpoint·서버 수신 활성화, 보안/운영·릴리스 검증과 사용자의 별도 승인 상태를 확인한다.
- 피드백 기능은 **2.0 완성을 기다리지 않고** 현재 v1 계열에서 먼저 배포하는 작업이다. 새로운 2.0의 기능 후보나 canonical 계약과 별도 추적한다.

### 5.2 피드백을 2.0 기획에 쓰는 방법(제안)

1. 사용자가 보고한 **구체적 상황·행동·불편**을 익명화된 문제 설명으로 요약한다. 원문·민감정보를 GitHub에 자동 복제하지 않는다.
2. (a) 기존 기능의 결함/마찰, (b) 원하는 미제공 기능, (c) 이미 있는 기능의 발견성 문제를 구분한다.
3. 같은 문제를 현재 v1.12.0 및 main 동작과 대조한다. 이미 해결된 문제인지, 버전 차이인지, 재현이 필요한지 명시한다.
4. 빈도뿐 아니라 불편의 강도, 영향받는 사용자, 해결 방법의 단순성, 기존 설정/호환성 영향, 검증 비용을 함께 고려한다. 자발적 응답은 전체 사용자의 대표 표본이라고 가정하지 않는다.
5. 후보마다 **유지 / 개선 / 신규 / 보류 / 제외** 결정과 근거, 승인 날짜, 참고 출처를 아래 결정 기록에 축적한다.
6. 제품 범위가 정리된 뒤 별도 canonical 문서와 구현 Issue를 만들고, 필요하면 구체적인 수용 기준/실제 Chrome 검증 기준을 확정한다.

사용자 피드백이 없다거나 적다는 이유만으로 필요성이 없다고 판정하지 않는다. 제품 텔레메트리 수집을 이 기획 문서가 승인하는 것도 아니다.
